# Invite and join a league — Implementation Plan

## Overview

S-05 turns the invite code from a string on a page into a working on-ramp: a friend joins a league
by typing the code or following a link, the league shows who is actually in it, a member can leave,
and an organizer can hand the league over. Membership is already keyed per `(user, league)` — this
slice adds the write paths, the roster read, and the screens around them (FR-007, FR-002, US-01).

## Current State Analysis

The membership model landed in F-01 and has been carrying the organizer's own row since S-03; what
is missing is every path *other* than "create a league".

- `LeagueMembership` exists (`src/server/PredictionLeague.Domain/Entities/League.cs:22-31`) with
  `Id`, `LeagueId`, `UserId`, `Role`, and is mapped with a unique index on `(LeagueId, UserId)`
  (`src/server/PredictionLeague.Infrastructure/Persistence/Configurations/LeagueMembershipConfiguration.cs:16`).
  The table shipped in the `InitialCreate` migration — **no new table is needed**, only a column.
- `UserId` is a bare `Guid` with **no FK** to `AspNetUsers` (documented at
  `LeagueMembershipConfiguration.cs:18`). The roster therefore resolves display names by an explicit
  join in Infrastructure, not by a navigation property.
- `InviteCode` is unique-indexed, generated by `RandomInviteCodeGenerator` over an
  unambiguous alphabet (no `I`/`L`/`O`/`0`/`1`), and already surfaced with a copy button
  (`src/client/src/routes/leagues/LeagueDetailPage.tsx:92-101`). The only missing piece server-side
  is a read *by* code — `ILeagueRepository.cs:5-7` names `GetByInviteCodeAsync` as S-05's job.
- Visibility convention is set: a caller who is neither organizer nor member gets **404**, a member
  who lacks a specific right gets **403** (`LeaguesController.cs:92-107`, `196-217`).
- **Deep links do not survive sign-in today.** `RequireAuth.tsx:20` passes `state.from`, but
  `SignInPage.tsx:25` unconditionally navigates to `/app`, and `GoogleSignInButton.tsx:34` hardcodes
  `returnUrl` to `/sign-in`. The server side is fine — `ResolveReturnUrl`
  (`AuthController.cs:204-222`) accepts any path on an allowed origin. An invite link is the first
  feature that needs this, so the fix belongs here.
- **Boundary debt is due.** `lessons.md:25-30` records that `LeaguesController` imports EF Core and
  catches `InviteCodeCollisionException` to retry, and says outright: revisit at S-05.

## Desired End State

A signed-in user who receives a code (or a link) ends up on the league's page as a member, and the
league page names everyone in it. A member can leave; an organizer hands the league to another
member first, then leaves like anyone else. The last member out deletes the league, so a league
created by mistake does not outlive everyone's interest in it. Verified by: joining from a second account, seeing both
names on the roster, leaving, and confirming the league disappears from that account's list.

### Key Discoveries:

- Membership schema and its uniqueness guarantee already exist — this slice is write paths + reads,
  not modelling (`LeagueMembershipConfiguration.cs:16`).
- The organizer is represented **twice**: as `League.OrganizerUserId` and as a `LeagueMembership`
  row with `Role = Organizer` (`LeaguesController.cs:158-161`). Every write here must keep the two
  in step — transfer is the operation that would silently desynchronize them.
- `AppDbContext` is an `IdentityDbContext`, so `Context.Users` is reachable from a repository
  without a new dependency — the roster join stays inside Infrastructure and returns a DTO, the
  pattern `MatchWithEventsDto` already set.
- `ListForUserAsync` is `OrganizerUserId == userId || Memberships.Any(...)`
  (`LeagueRepository.cs:22-28`), so a joined league appears in "My leagues" with no query change.
- SQL Server's default collation is case-insensitive, so a lowercase code would match by accident.
  Normalizing input explicitly makes the behavior intentional rather than collation-dependent.

## What We're NOT Doing

- **No invite-code rotation or revocation.** The code is fixed for the league's lifetime.
- **No email/SMS invitations.** Sharing stays manual: copy the code or the link.
- **No organizer-initiated removal of a member** (kick). A member leaves on their own.
- **No standalone delete endpoint.** A league is deleted in exactly one situation: its last
  remaining member leaves. An organizer with other members still transfers first — there is no
  "delete this league" control, and no way to remove a league that other people are in.
- **No join-time blocking on a started tournament.** Late joiners are allowed; the kickoff lock in
  S-06 is what prevents predicting matches that already happened.
- **No predictions, standings, or points.** S-06 and S-07 own those.
- **No FK from `LeagueMembership.UserId` to `AspNetUsers`.** The join stays explicit, as S-03 chose.
- **No tests.** Neither unit exists has a test suite; verification is build + lint + manual.

## Implementation Approach

Four phases, deployable in pairs. The server phases (1-2) are additive — new endpoints and one
nullable-free column with a default — so they can ship before the client without breaking the
shipped UI. The client phases (3-4) then light them up.

Two invariants drive the design:

1. **Organizer identity is single-sourced at write time.** `League.OrganizerUserId` is the
   authority; the `Role = Organizer` membership row mirrors it. Transfer updates both in one
   `SaveChangesAsync`, and leave refuses while the caller is the organizer — so the pair can never
   drift.
2. **Unknown code and invisible league look identical.** Joining with a bad code returns 404 with a
   generic message, matching the masking rule the controller already applies to league reads.

## Critical Implementation Details

**Join idempotency has a race.** Two rapid submissions of the same code by the same user both pass
the "already a member?" check and both insert, and the unique index on `(LeagueId, UserId)` rejects
the second. The repository translates that violation into "already a member" and returns success —
the same outcome as the checked path — so the endpoint stays idempotent under concurrency. Follow
the precedent in `LeagueRepository.IsInviteCodeCollision` (`LeagueRepository.cs:116-118`): match on
SQL error 2601/2627 **and** the index name, so an unrelated write failure is not swallowed.

**Transfer and leave must be one save each.** Transfer writes `OrganizerUserId`, demotes the old
organizer's row to `Member`, and promotes the target's row to `Organizer`. A partial save here
produces a league whose organizer flag and role rows disagree — the one state no read path checks
for.

## Phase 1: Server — data layer

### Overview

Add the joined-at column, the read-by-code, the three membership writes, and the roster projection.
Move the invite-code collision retry out of the controller while the same code path is open.

### Changes Required:

#### 1. Membership timestamp

**File**: `src/server/PredictionLeague.Domain/Entities/League.cs`
**File**: `src/server/PredictionLeague.Infrastructure/Persistence/Configurations/LeagueMembershipConfiguration.cs`

**Intent**: Record when each member joined, so the roster has a stable, meaningful order and the
moment of joining is recoverable later. Backfilling this after the fact is impossible.

**Contract**: `LeagueMembership.JoinedUtc` as a non-nullable `DateTimeOffset`, configured with
`builder.Property(m => m.JoinedUtc).HasDefaultValueSql("SYSUTCDATETIME()")` in
`LeagueMembershipConfiguration`. The `HasDefaultValueSql` is what puts a real timestamp on existing
rows — without it `dotnet ef migrations add` scaffolds `defaultValue: 0001-01-01T00:00:00+00:00`
for a required column and backdates every current membership to year 1. Stamping the value in
migration time is acceptable here: a handful of local rows, no production leagues that matter.
Set it explicitly on every insert anyway, including the organizer's row in
`LeaguesController.Create`, so join time never depends on the database clock default.

#### 2. Migration

**File**: `src/server/PredictionLeague.Infrastructure/Persistence/Migrations/` (new)

**Intent**: Apply the single new column.

**Contract**: `dotnet ef migrations add AddLeagueMembershipJoinedUtc --project src/server/PredictionLeague.Infrastructure --startup-project src/server/PredictionLeague.Api`.
One `AddColumn` on `LeagueMemberships` with a default value; no table, no index change. Dev
auto-migrates on startup; prod stays forward-only and human-gated.

#### 3. Roster projection

**File**: `src/server/PredictionLeague.Application/Abstractions/Persistence/LeagueMemberDto.cs` (new)

**Intent**: Carry a member's identity to the Api layer without exposing Identity types or forcing
the controller to know how names are resolved.

**Contract**: `record LeagueMemberDto(Guid UserId, string DisplayName, MembershipRole Role, DateTimeOffset JoinedUtc)`.
Sits beside `MatchWithEventsDto` in the same namespace, mirroring its role as a read-side
projection.

#### 4. Repository contract and implementation

**File**: `src/server/PredictionLeague.Application/Abstractions/Persistence/ILeagueRepository.cs`
**File**: `src/server/PredictionLeague.Infrastructure/Persistence/Repositories/LeagueRepository.cs`

**Intent**: Give the controller every membership operation this slice needs, with persistence
concerns — including unique-violation handling — ending at this boundary.

**Contract**: four additions.

- `Task<League?> GetByInviteCodeAsync(string inviteCode, CancellationToken)` — tracked, includes
  `Memberships` **and `ScoringRules`**; the join path both reads and writes it. The rules are not
  optional: the join response is a full `LeagueDetailResponse`, `ToDetailResponse` enumerates
  `league.ScoringRules` (`LeaguesController.cs:281`), and lazy loading is off
  (`DependencyInjection.cs:36` registers plain `UseSqlServer`, no proxies) — so a missing `Include`
  ships `scoringRules: []` silently rather than failing.
- `Task JoinAsync(League league, Guid userId, CancellationToken)` — inserts a `Member` row with
  `JoinedUtc = DateTimeOffset.UtcNow` and saves. **Returns normally when the user is already a
  member**, whether detected by the pre-check or by the unique-index violation on
  `IX_LeagueMemberships_LeagueId_UserId`. Any other `DbUpdateException` propagates.
- `Task LeaveAsync(League league, Guid userId, CancellationToken)` — removes the caller's membership
  row and saves. Returning normally when no row exists keeps the endpoint idempotent. **When that
  row is the league's only membership, the league itself is removed instead** — one
  `SaveChangesAsync`, with `ScoringRules` and the membership going out on the cascade already
  configured at `LeagueConfiguration.cs:19-27`, so an empty league is never left behind. Deciding
  between the two is a count on the tracked `league.Memberships`, not a second query.
- `Task TransferOrganizerAsync(League league, Guid newOrganizerUserId, CancellationToken)` — sets
  `league.OrganizerUserId`, flips the outgoing organizer's row to `Member` and the target's to
  `Organizer`, and saves **once**. Throws `InvalidOperationException` if the target has no membership
  row — the controller validates first, so this is a guard, not a control path.
- `Task<IReadOnlyList<LeagueMemberDto>> ListMembersAsync(Guid leagueId, CancellationToken)` — joins
  `LeagueMemberships` to `Context.Users` on `UserId`, ordered by `JoinedUtc`. A member whose user row
  is missing is skipped rather than surfaced with an empty name.

Follow `ReplaceScoringRulesAsync`'s precedent: the write methods take a **tracked** league from a
tracked read and throw a clear `InvalidOperationException` when handed a detached one
(`LeagueRepository.cs:54-56`).

#### 5. Boundary debt: collision retry moves into the repository

**File**: `src/server/PredictionLeague.Infrastructure/Persistence/Repositories/LeagueRepository.cs`
**File**: `src/server/PredictionLeague.Application/Abstractions/Persistence/ILeagueRepository.cs`
**File**: `src/server/PredictionLeague.Api/Controllers/LeaguesController.cs`
**File**: `src/server/PredictionLeague.Application/Abstractions/Leagues/InviteCodeCollisionException.cs`

**Intent**: Settle the debt `lessons.md:25-30` recorded against this slice. The controller currently
catches a persistence-signalled exception and re-drives the insert; that retry belongs behind the
repository, so the Api layer stops reasoning about write failures at all.

**Contract**: `CreateAsync` owns the retry, but takes the generator as a **parameter, not a
dependency**: `Task CreateAsync(League league, Func<CancellationToken, Task<string>> nextCode, CancellationToken)`.
The controller passes `_inviteCodes.GenerateAsync`. On a collision the repository re-codes the
still-tracked league from `nextCode` and saves once more; after that budget is spent it throws
`InviteCodeCollisionException`, which the controller maps to 503 — one `catch` of a domain
exception, no EF Core import. Delete the `using Microsoft.EntityFrameworkCore;` from
`LeaguesController.cs:4` and the nested retry at `LeaguesController.cs:164-184`.
`RandomInviteCodeGenerator`'s own pre-check probe stays as-is.

**Do not constructor-inject `IInviteCodeGenerator` into `LeagueRepository`.**
`RandomInviteCodeGenerator` already depends on `ILeagueRepository` for that probe
(`RandomInviteCodeGenerator.cs:18-23`) and both are `AddScoped`
(`DependencyInjection.cs:39`, `:49`), so a constructor edge would close a DI cycle —
`ILeagueRepository` → `IInviteCodeGenerator` → `ILeagueRepository`. That failure is a
resolve-time throw, not a compile error: the build stays green while every league route 500s.
The delegate parameter keeps the retry behind the boundary without the edge.

## Phase 2: Server — membership API

### Overview

Three new endpoints plus the roster on the league detail response.

### Changes Required:

#### 1. Join by invite code

**File**: `src/server/PredictionLeague.Api/Controllers/LeaguesController.cs`

**Intent**: Turn a code into membership, and make a repeated join a no-op that still lands the user
on the league — a re-clicked link from a chat thread is a normal event, not an error.

**Contract**: `POST /api/leagues/join`, body `record JoinLeagueRequest(string InviteCode)`,
`[Authorize]`. Normalizes the code (`Trim().ToUpperInvariant()`) before lookup so matching does not
depend on collation. Unknown or blank code → **404** with a generic "No league found for that invite
code." Success and already-a-member both → **200** with the same `LeagueDetailResponse` shape the
detail route returns, so the client can render the league immediately without a second round trip.
The organizer using their own code is just the already-a-member case.

#### 2. Leave a league

**File**: `src/server/PredictionLeague.Api/Controllers/LeaguesController.cs`

**Intent**: Let a member undo a join without asking anyone, and let a solo organizer abandon a
league nobody else joined — otherwise creating a league is permanently undoable.

**Contract**: `DELETE /api/leagues/{id:guid}/membership`, `[Authorize]`. Non-member → **404**
(masking, as everywhere else). Caller is the organizer **and other members exist** → **409** with
"Transfer the league to another member before leaving." Caller is the **only** member → **204**, and
the league is deleted with it (see `LeaveAsync`). Otherwise removes the row and returns **204**.

The last-member case is the only path that destroys a league, and it can only ever destroy one the
caller is alone in — an organizer cannot delete a league out from under members, because the 409
fires first.

#### 3. Transfer the organizer role

**File**: `src/server/PredictionLeague.Api/Controllers/LeaguesController.cs`

**Intent**: Hand the league to another member so the outgoing organizer can then leave by the normal
path. Also useful on its own.

**Contract**: `PUT /api/leagues/{id:guid}/organizer`, body `record TransferOrganizerRequest(Guid UserId)`,
`[Authorize]`. Caller not organizer → **403** if they are a member, **404** if they are not (the
existing two-step check at `LeaguesController.cs:211-217`). Target is not a member of this league →
**400** "That user is not a member of this league." Target equals the caller → **400**. Success →
**200** with the refreshed detail, where `isOrganizer` is now `false` for the caller.

#### 4. Roster on the detail response

**File**: `src/server/PredictionLeague.Api/Controllers/LeaguesController.cs`

**Intent**: Answer "who is in this league" — `memberCount` alone cannot tell an organizer whether
the right friend joined.

**Contract**: Extend `LeagueDetailResponse` with
`IReadOnlyList<LeagueMemberResponse> Members`, `record LeagueMemberResponse(Guid UserId, string DisplayName, MembershipRole Role, DateTimeOffset JoinedUtc)`.
Visible to every member of the league (same audience as the invite code itself). `GET`, `POST`,
`POST /join`, `PUT /scoring-rules`, and `PUT /organizer` all return it, so `ToDetailResponse` takes
the member list as a parameter the way it already takes `isScoringLocked`
(`LeaguesController.cs:271`). Each of those five routes sources that list from
`ListMembersAsync(league.Id, …)` called **after** its own save — `Memberships` on the tracked graph
carries no display names, and on `POST` and `POST /join` the caller's own row does not exist until
the save completes. `MemberCount` stays — the list page uses it and does not fetch the
roster. The list endpoint is deliberately untouched.

**File**: `src/server/PredictionLeague.Api/PredictionLeague.http`

**Intent**: Keep the sample-request file usable for manual verification of the new routes.

**Contract**: One request per new endpoint, following the file's existing style.

### Success Criteria:

#### Automated Verification:

- Server builds: `cd src/server && dotnet build`

#### Manual Verification:

- Second account joins with a valid code → 200, league appears in that account's `GET /api/leagues`
- Joining the same code again → 200 (not 409), member count unchanged
- Unknown / blank / lowercase-of-a-valid code: unknown and blank → 404; lowercase valid → 200
- `GET /api/leagues/{id}` returns both members with display names and roles, oldest first
- Member leaves → 204, and the league disappears from their list; organizer's `memberCount` drops
- Organizer attempts to leave while another member is present → 409
- Organizer of a solo league leaves → 204, the league is gone from `GET /api/leagues`, and its

- Transfer to a member → 200, `isOrganizer` flips for both accounts; old organizer can then leave
- Transfer to a non-member id → 400; transfer by a member → 403; by a stranger → 404

## Phase 3: Client — the join flow

### Overview

The code-entry screen, the shareable link, and the sign-in round trip that a link needs in order to
survive.

### Changes Required:

#### 1. Types

**File**: `src/client/src/leagues/types.ts`

**Intent**: Mirror the extended server contract.

**Contract**: `LeagueMember` (`userId`, `displayName`, `role: "Organizer" | "Member"`, `joinedUtc`)
and `members: LeagueMember[]` on `LeagueDetailResponse`. Keep the "mirrors LeaguesController's
response records" comment accurate by noting S-05.

#### 2. Join page

**File**: `src/client/src/routes/leagues/JoinLeaguePage.tsx` (new)
**File**: `src/client/src/routes/index.tsx`

**Intent**: One screen serving both entry paths — typed code and followed link.

**Contract**: Routes `/app/leagues/join` and `/app/leagues/join/:code`, both under `RequireAuth`.
The `:code` variant prefills the input from the URL param; it does **not** auto-submit, so following
a link is a decision rather than a side effect. Submit → `POST /api/leagues/join`, then
`navigate("/app/leagues/{id}", { replace: true })` on success. `ApiError` 404 → inline "No league
found for that invite code." Input is uppercased as the user types, matching the generator's
alphabet.

#### 3. Deep-link survival through sign-in

**File**: `src/client/src/routes/SignInPage.tsx`
**File**: `src/client/src/auth/GoogleSignInButton.tsx`

**Intent**: An anonymous user following an invite link currently lands on `/app` after signing in
and loses the code. Both sign-in paths must return them to where they were headed.

**Contract**: One destination, two carriers. `RequireAuth.tsx:20` sets `state.from` to a **Location
object**, so the path is `from.pathname + from.search` — never `${from}`, which stringifies to
`[object Object]`.

- `SignInPage`, when authenticated, navigates to the first of: `location.state?.from` (survives the
  in-SPA email path), a `returnTo` query param, `/app`.
- `GoogleSignInButton` cannot use router state — the Google round trip is a full page navigation —
  so it encodes the destination into the return URL it hands the server:
  `${window.location.origin}/sign-in?returnTo=${encodeURIComponent(path)}`. It reads the same
  `from` via `useLocation()`.

**`returnUrl` keeps pointing at `/sign-in`, not at the destination.** `ExternalCallback` reports
every external-login failure by appending `?error=` to `returnUrl`
(`AuthController.cs:139`, `155`, `163`, `173`, `177`) — including `account_exists`, which any user
with a local account of the same email will hit. `SignInPage` is the only screen that renders those
codes (`SignInPage.tsx:13`, `messageForExternalError`). Sending `returnUrl` straight to
`/app/leagues/join/:code` would drop an unauthenticated user on a `RequireAuth` route, bounce them
back to `/sign-in`, and strip the error — a silent failure on every Google path, not just invites.

Because `returnTo` now arrives through the query string, `SignInPage` validates it before
navigating: it must start with a single `/` and not with `//` or `/\`, so it can only ever be a
same-origin relative path. The server's own origin check (`AuthController.cs:204-222`) is unchanged
and no server edit is needed.

#### 4. Entry points

**File**: `src/client/src/routes/AppShell.tsx`
**File**: `src/client/src/routes/leagues/LeaguesListPage.tsx`

**Intent**: Make joining discoverable — today the only league action offered anywhere is "create".

**Contract**: A "Join a league" button beside "My leagues" on the shell, and beside "New league" on
the list page. The list's empty-state copy stops assuming creation is the only option.

#### 5. Shareable link on the detail page

**File**: `src/client/src/routes/leagues/LeagueDetailPage.tsx`

**Intent**: Give the organizer the thing they actually paste into a chat.

**Contract**: Alongside the existing code + Copy control, a "Copy invite link" button writing
`${window.location.origin}/app/leagues/join/${inviteCode}`. Reuse the existing copied-state pattern
(`LeagueDetailPage.tsx:38-47`) rather than adding a second mechanism.

## Testing Strategy

No test suite exists in either unit, so verification is build + lint + a scripted two-account manual
pass.

### Manual Testing Steps:

1. Sign in as account A, create a league on a published tournament, copy the invite link.
2. In a second browser profile, open the link **signed out**; sign in as account B; land on the
   prefilled join page; join.
3. Confirm the league page lists A and B, A badged Organizer.
4. Re-open the same link as B → join again → lands on the league, member count still 2.
5. As B, leave; confirm the league vanishes from B's list and A sees one member.
6. Re-join as B. As A, attempt to leave → the UI offers no Leave; call the endpoint directly → 409.
7. As A, transfer to B → A's badge becomes Member, B can edit scoring rules.
8. As A, leave → succeeds; B remains the only member and the organizer.
8b. As B, leave the now-solo league → the league is deleted; it is gone from B's list and
    `GET /api/leagues/{id}` returns 404.
9. Try a garbage code, a lowercase valid code, and a blank submit on the join page.

## Performance Considerations

The detail read gains one join against `AspNetUsers` scoped to a single league's memberships — a
handful of rows at friend-group scale. The list endpoint is deliberately left alone so it does not
become N+1 in the member count; it keeps using the already-loaded `Memberships.Count`.

## Migration Notes

One additive column (`LeagueMemberships.JoinedUtc`) with a migration default, so the migration is
safe to apply before the new code deploys and safe to leave in place if the code is rolled back.

**Phase ordering across the deploy boundary**: phases 1-2 are additive and can ship alone — the
